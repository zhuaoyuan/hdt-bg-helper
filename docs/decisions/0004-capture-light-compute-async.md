# ADR-0004：插件采集保持轻量，原始数据只追加，计算异步化

- **状态：** accepted（所有者 2026-10-05 对话确认完成 P2-T1；正文按同日重估细化后再接受）
- **日期：** 2026-09-25（细化 2026-10-05）
- **相关：** P2、P4、`design/P2-data-capture.md`、ADR-0010、`context/early_discussion.md`（A3 第二节）

## 背景

- HDT 的事件处理和 `OnUpdate()`（约 100ms 一次）都跑在 HDT 自己的流程里，插件在这里做重活会拖慢 HDT 甚至游戏体验。
- Bob's Buddy 单场模拟就要 1.5–5 秒、占用一半 CPU 核心（`facts/bobsbuddy-simulator-input.md`），战力分位需要对很多参照场面做模拟，计算量远大于此。
- 字段含义可能随游戏版本变化，今天认为无用的标签以后可能需要。
- P1 诊断插件已证明：局内只转储、离线再分析可行；`records.jsonl` 约 10–28 MB/局，需要压缩与保留策略（`facts/diag-capture-measured.md`、`facts/diag-capture-batch-20261003.md`）。
- P2 范围重估后：不另造采集插件与三层 schema 演进体系（`worklog/2026-10-05-p2-rescope.md`）。

## 决定

1. **采集与计算分离。** 插件在游戏事件里只做读取、标记阶段、写入本地；模拟和分位计算放到后台线程或独立进程（含现有 `spikes/replay-harness` 与后续 P3 引擎）。
2. **两层够用，第三层按需缓存。**
   - **原始层** = 诊断记录目录格式（`meta.json`、`records.jsonl[.gz]`、`power.log.gz`），按时间顺序只追加（局内），带 `schemaVersion` 与插件/HDT/BB 版本。
   - **标准层** = 离线导入生成的每回合表（完整性标签、战果来源、Input/Output 引用等），可从原始层 + 团子文本重新生成。
   - **模拟层** = 不强制独立存储图式；重放结果与分位缓存由工具/引擎按需写出，须能从原始或标准层复算。
3. **不单独设计 schema 演进框架。** 跨版本差异用 `meta` 中的 BB/HDT 版本分桶 + 导入侧适配处理。
4. **本地存储**，不上传。玩家标识在本地匿名化。
5. **压缩：** 对局结束后压缩 `records.jsonl`；导入同时支持未压缩历史文件。
6. 插件生命周期可关闭、可卸载，并记录自身版本。

主数据源取舍见 [ADR-0010](0010-hdt-input-dump-as-primary-source.md)。细则见 [`design/P2-data-capture.md`](../design/P2-data-capture.md)。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 为什么没选 / 为什么选 |
| --- | --- | --- | --- |
| 只存 CSV | 简单 | 丢失标签、未知字段和事件顺序，无法重新解析 | 没选 |
| 插件内直接算分 | 少组件 | 阻塞 HDT；难以复算 | 没选 |
| 完整三层 + schema 迁移体系 | 理论上最稳 | 对个人规模过重；诊断格式已够用 | 没选 |
| **原始只追加 + 离线投影 + 异步计算** | 可重放、可复算、不影响 HDT；复用已有 diag | 原始体积较大 | **选中** |

## 后果

- 正面：采集逻辑简单、稳定；历史数据可重解析；与已采样本兼容。
- 代价：原始数据体积仍大；导入脚本要处理脏数据与多版本。
- 跟进：P2-T2 压缩与匿名化；P2-T3 标准层；P4 实时显示再评估延迟预算。

## 推翻条件

实测显示原始层体积或写入开销不可接受；或反射主路径长期失效且实体重建成本不可接受（与 ADR-0010 一并重评）。
